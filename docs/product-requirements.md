# ข้อกำหนดผลิตภัณฑ์

## เป้าหมายและขอบเขต

กิจการเดียวมีสองร้านคนละสถานที่: ก๋วยเตี๋ยวและเบเกอรี่ ผู้ใช้หลักคือแม่บน Android Chrome
ต้องแสดงร้านเสมอ ใช้ภาษาไทย อ่านง่าย ปุ่มใหญ่ ลดขั้นตอน และยืนยันผลจาก server ก่อนแจ้งสำเร็จ
โค้ด ชื่อตาราง API และ error codes ใช้ภาษาอังกฤษ

MVP ครอบคลุม login, เลือกร้าน, เมนู/ราคา, บัญชีเงินจริง, ขายรายบิลพร้อมส่วนลดและแบ่งชำระ,
ยอดขายเพิ่มเติม, กระทบยอดทั้งวัน, รายจ่ายค้างจ่าย/จ่ายเต็ม, เติมทุน/ถอน, โอนเงิน,
คืนเงินเต็มบิล, ตรวจเงินสด/ปิดวัน/เปิดแก้ไข, ประวัติ, audit และรายงานแยกร้าน/ทั้งกิจการ
ทุกธุรกรรมเงินต้อง atomic และ retry ได้โดยไม่ซ้ำ รายงานแยกยอดขายสุทธิ รายจ่าย และกระแสเงินสด
ไม่เรียกส่วนต่างยอดขายกับรายจ่ายว่า “กำไรสุทธิ”

ไม่รวมสต็อก สูตรอาหาร ต้นทุนขาย การผลิต VAT/ภาษีเต็มรูปแบบ เครดิตลูกค้า ผ่อนจ่าย
คืนบางรายการ ไฟล์แนบ offline queue และอุปกรณ์ POS พิเศษ ไม่มีข้อมูลยอดสมมติในรายงานจริง
หลักฐาน MVP เก็บข้อความอ้างอิงได้ ยังไม่มี upload/download

## ข้อกำหนดที่ล็อกแล้ว

React + TypeScript + Vite; Express + TypeScript; PostgreSQL; modular monolith;
REST `/api/v1`; online-first; Asia/Bangkok; ตรวจสิทธิ์บน backend ทุก request
ข้อมูลธุรกรรมยืนยันแล้วไม่ hard delete ไม่มีการปรับเงินหรือยอดขายเงียบ ๆ

## ค่าเริ่มต้นทางเทคนิค

ใช้ npm workspaces และ lockfile เดียว, Drizzle สำหรับ schema/migration ที่อ่าน SQL ได้,
Zod validate request, PostgreSQL-backed sessions, Pino/pino-http ที่ redact secrets,
Vitest/Supertest และ PostgreSQL จริงสำหรับ integration, Docker Compose สำหรับ local DB
Tailwind ใช้ utility สำหรับ mobile layout ร่วมกับ tokens ขนาดเล็ก ไม่มี UI framework เพิ่มใน foundation
เลือก Caddy เป็นข้อเสนอ deployment ภายหลัง ยังไม่ติดตั้ง/เผยแพร่
ไม่กำหนดเลขเวอร์ชัน package จากความจำ: ตรวจ official documentation และ pin เมื่อเริ่ม foundation

## การตัดสินใจทางธุรกิจ

| ID | ข้อเสนอ | เหตุผล/ผลกระทบ |
|---|---|---|
| P1 ยืนยันแล้ว | ยอดจริงทั้งวันเป็นยอดสุทธิหลังคืนเงิน; คืนข้ามวันมีผลวันที่คืน | ผู้ใช้ยืนยันใน session วันที่ 22 ตุลาคม 2026; ไม่เปลี่ยนวันปิดย้อนหลัง |
| P2 ยืนยันแล้ว | opening cash เป็น snapshot ยอด ledger ยกมา; variance ไม่ post อัตโนมัติ | ผู้ใช้ยืนยันให้ OWNER อนุมัติปรับส่วนต่างแยกก่อนเปิดวันถัดไป |
| P3 ยืนยันแล้ว | ผู้ใช้เริ่มต้นทั้งสองเป็น OWNER; refund/reopen/reversal เป็น OWNER เท่านั้น | ผู้ใช้ยืนยันสิทธิ์เริ่มต้นใน session เดียวกัน |
| P4 ยืนยันแล้ว | ห้ามบัญชีติดลบ; เปิดวันใหม่เมื่อวันก่อนปิดและเคลียร์แล้ว; ข้ามเที่ยงคืนยังไม่รองรับ | ตรวจสอบเงินก่อนใช้งานต่อ; บัญชีธนาคารร่วมต้องตั้งยอดจริงก่อน |
| P5 ยืนยันแล้ว | ไม่มีภาษี/ค่าบริการ; ส่วนลดจำนวนเงินหรือเปอร์เซ็นต์ระดับบิล | จำกัดขอบเขต POS ให้ตรวจสอบได้ |

P1–P5 ได้รับการยืนยันจากผู้ใช้แล้ว; P4/P5 ยืนยันใน session วันที่ 22 ตุลาคม 2026
P4 ยืนยันให้วันก่อนปิดและเคลียร์ก่อนเปิดวันใหม่ ห้ามบัญชีติดลบ และยังไม่รองรับการขายข้ามเที่ยงคืน
เริ่ม S1/S2 ตามกฎที่ยืนยันได้แล้ว

## ความคลุมเครือและข้อขัดแย้งที่แก้ในแบบ

“ยอดจริงต่ำกว่ายอดบันทึก” ไม่ใช่ refund อัตโนมัติ ต้องเข้ากระบวนการแก้ไข
ยอดรับเงินอาจต่างยอดขายเมื่อคืนข้ามบัญชี: reconciliation ใช้บัญชีรับเดิมเพื่อจัดกลุ่มยอดขาย
ส่วน ledger ใช้บัญชีที่จ่ายคืนจริง แสดงสองมุมบน preview ไม่ใช้ยอดเงินในบัญชีแทนยอดขาย
บัญชีธนาคารร่วมมี identity เดียว ใช้ store attribution ใน movement ไม่สร้างยอดธนาคารซ้ำสองร้าน
ปิดเงินสดไม่ปรับ ledger จน OWNER ยืนยัน adjustment; จึงต้องมีขั้นตอนเคลียร์ก่อนวันถัดไป

## ผลส่งมอบรอบนี้

เอกสารและสัญญาที่ตรวจสอบได้ พร้อมกรณี A–P และแผนงาน ไม่มี business implementation
การตรวจรอบนี้เป็นการ review เอกสาร ไม่ใช่หลักฐานว่า constraints, security หรือ concurrency ใช้งานได้จริง
