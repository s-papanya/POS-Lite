# 1. บริบทและเป้าหมาย

ฉันต้องการสร้างระบบให้แม่ใช้บริหารร้านอาหารขนาดเล็ก 2 ร้าน ได้แก่:

1. ร้านก๋วยเตี๋ยว
2. ร้านเบเกอรี่

สองร้านอยู่คนละสถานที่ แต่มีเจ้าของเดียวกัน ต้องดูข้อมูลแยกร้านและภาพรวมกิจการได้

แม่ใช้มือถือ Android เป็นอุปกรณ์หลัก ระบบจึงต้องใช้งานสะดวกบนมือถือ ภาษาไทย อ่านง่าย ปุ่มใหญ่ และลดจำนวนขั้นตอนในการบันทึกข้อมูล

เป้าหมายหลักคือ:

- บันทึกยอดขายได้สะดวก
- รู้ว่าเงินเข้าออกจากอะไร
- รู้ยอดเงินสดและบัญชีรับโอนแยกร้าน
- ปิดยอดประจำวันและตรวจสอบเงินขาดเกินได้
- ลดการจดข้อมูลกระจัดกระจาย
- ต่อไปสามารถคำนวณต้นทุนสูตรอาหาร จัดการวัตถุดิบ และติดตามการผลิตเบเกอรี่ได้

ระบบต้องให้ความสำคัญกับความถูกต้องของธุรกรรมและความง่ายในการใช้ มากกว่าจำนวนฟีเจอร์หรือความซับซ้อนของเทคโนโลยี

อย่าสมมติว่าร้านมีเครื่องสแกนบาร์โค้ด เครื่องพิมพ์ใบเสร็จ ลิ้นชักเงินอัตโนมัติ หรือระบบรับชำระเงินที่เชื่อม API อยู่แล้ว

# 2. วิธีสื่อสารและทำงาน

- อธิบายและสรุปงานเป็นภาษาไทย
- ใช้ภาษาอังกฤษสำหรับโค้ด ชื่อตัวแปร ตาราง API และข้อความทางเทคนิคในระบบ
- ข้อความบนหน้าจอสำหรับแม่ให้เป็นภาษาไทย
- บอกสิ่งที่ทำจริง สิ่งที่ทดสอบแล้ว และสิ่งที่ยังไม่รองรับอย่างตรงไปตรงมา
- อย่าอ้างว่าระบบพร้อมใช้งานจริงเพียงเพราะ build ผ่าน
- ตรวจ repository และอ่าน AGENTS.md ถ้ามีก่อนแก้ไขไฟล์
- หากมีโค้ดเดิม ให้ประเมินและต่อยอด ห้ามเขียนทับโดยไม่ตรวจสอบ
- ตัดสินใจเรื่อง implementation ทั่วไปได้เองตามความเหมาะสม
- ถ้าข้อมูลไม่ครบ ให้เสนอค่าเริ่มต้นพร้อมเหตุผลและบันทึก assumption
- ถ้าความคลุมเครือมีผลต่อความหมายของยอดขาย เงิน สต็อก หรือสิทธิ์ ให้ถามเฉพาะประเด็นสำคัญเป็นชุดสั้น ๆ
- ระหว่างรอคำตอบ ให้ทำงานส่วนที่ไม่ขึ้นกับคำตอบต่อได้
- ไม่เพิ่มฟีเจอร์นอกขอบเขตโดยไม่มีเหตุผล
- อย่าเริ่มจากทำ Dashboard สวย ๆ แล้วใช้ตัวเลขสมมติมาทดแทนธุรกรรมจริง

# 3. Technology และ Architecture

ข้อกำหนดที่ตัดสินใจแล้ว:

- Frontend: React + TypeScript + Vite
- Backend: Express.js + TypeScript
- Database: PostgreSQL
- รูปแบบระบบ: Modular Monolith
- API: REST ภายใต้ /api/v1
- ใช้งานผ่านเว็บที่รองรับมือถือ และออกแบบเผื่อ Android PWA
- MVP ใช้งานออนไลน์เป็นหลัก

ฉันชอบ Express.js ให้ใช้ Express เป็น Backend หลัก ไม่เปลี่ยนเป็น Fastify หรือ Framework อื่นเอง

เทคโนโลยีที่เสนอให้ประเมินก่อนเลือก:

- Tailwind CSS สำหรับ styling
- Drizzle ORM สำหรับฐานข้อมูลและ migration
- Zod สำหรับ validation
- Session-based authentication
- Pino และ pino-http สำหรับ logging
- Vitest และ Supertest สำหรับ testing
- Docker Compose สำหรับ local PostgreSQL
- Caddy หรือ Nginx สำหรับ deployment ในอนาคต

ส่วนที่ยังไม่ล็อกให้เลือกโดยอธิบายสั้น ๆ ว่าเหมาะกับโปรเจกต์นี้อย่างไร ไม่ต้องเปรียบเทียบทุก library อย่างยืดยาว

ยังไม่ต้องใช้:

- Microservices
- Kubernetes
- Redis
- Message broker
- Event sourcing เต็มรูปแบบ
- ระบบบัญชีแยกประเภททั่วไปเต็มรูปแบบ

หากพบความจำเป็นจริง ให้เสนอพร้อมปัญหาที่ต้องแก้ก่อนเพิ่ม dependency

# 4. ผู้ใช้และสิทธิ์

ช่วงแรกมีฉันกับแม่ แต่ต้องรองรับพนักงานในอนาคต

บทบาทตั้งต้น:

OWNER
- เข้าถึงทั้งสองร้าน
- ดูรายงานรวม
- จัดการผู้ใช้และสิทธิ์
- จัดการเมนู ราคา และบัญชี
- อนุมัติรายการแก้ไขหรือเปิดรอบแก้ไขวันที่ปิดแล้ว

MANAGER
- จัดการร้านที่ได้รับสิทธิ์
- ดูยอดขาย รายจ่าย และปิดวัน
- ไม่มีสิทธิ์จัดการข้อมูลทั้งกิจการโดยอัตโนมัติ

STAFF
- บันทึกขายและดูข้อมูลที่จำเป็นในร้านที่ได้รับสิทธิ์
- ไม่มีสิทธิ์ดูรายงานทางการเงินทั้งหมดหรือเปิดวันที่ปิดแล้ว

ให้ทำ permission matrix ก่อน implementation โดยระบุว่าบทบาทใดทำอะไรได้บ้าง และแยก business-level permission ออกจาก store-level permission

Backend ต้องตรวจสิทธิ์ทุกคำขอ ไม่เชื่อ store_id จาก client โดยไม่ตรวจสอบ และไม่ใช้การซ่อนปุ่มเป็นมาตรการรักษาสิทธิ์เพียงอย่างเดียว

# 5. ขอบเขต MVP

MVP ต้องรองรับกระบวนการใช้งานจริงต่อไปนี้ครบ:

1. เข้าสู่ระบบ
2. เลือกร้าน
3. ตั้งเมนูและราคา
4. ตั้งบัญชีเงินสดและบัญชีรับโอน
5. บันทึกยอดขายรายบิล
6. บันทึกยอดขายแบบสรุป
7. ใช้รายบิลร่วมกับยอดสรุปโดยไม่เกิดยอดขายซ้ำ
8. บันทึกรายจ่ายและการชำระเงินจริง
9. บันทึกเงินเติมทุนและถอนใช้ส่วนตัว
10. โอนเงินระหว่างบัญชีของกิจการ
11. ตรวจนับเงินสด
12. ปิดวัน
13. ดูประวัติและรายงานพื้นฐาน
14. เก็บประวัติการแก้ไขธุรกรรมสำคัญ

รายงาน MVP ให้แสดงยอดขาย รายจ่าย และกระแสเงินสดอย่างถูกความหมาย

ยังไม่ต้องอ้างว่าเป็นกำไรสุทธิจริง เพราะยังไม่มีระบบต้นทุนและสต็อกครบ

# 6. วิธีบันทึกยอดขาย

ต้องรองรับทั้ง 3 รูปแบบต่อไปนี้ในร้านเดียวกัน

## 6.1 POS รายบิล

- เลือกเมนู
- เพิ่มหรือลดจำนวน
- แสดงราคาต่อหน่วยและยอดรวม
- รองรับส่วนลดระดับบิลอย่างง่าย โดยกำหนดวิธีคำนวณและปัดเศษให้ชัดเจน
- รับเงินสดหรือเงินโอน
- รองรับการแบ่งชำระเงินสดและโอนในบิลเดียว
- เงินโอนต้องระบุบัญชีปลายทาง
- เงินสดต้องระบุบัญชีเงินสดที่เกี่ยวข้อง
- เงินทอนต้องแยกจากยอดรับชำระสุทธิของบิล
- ยืนยันสำเร็จแล้วต้องมีเลขอ้างอิงและดูย้อนหลังได้

Backend ต้องคำนวณยอดจากข้อมูลที่เชื่อถือได้ ไม่รับยอดรวมที่ client ส่งมาเป็นข้อเท็จจริงโดยไม่ตรวจสอบ

ราคากับชื่อสินค้าขณะขายต้องถูกเก็บเป็น snapshot เพื่อให้การเปลี่ยนเมนูหรือราคาในอนาคตไม่เปลี่ยนบิลเก่า

หากราคาเปลี่ยนหลัง client โหลดเมนู ให้กำหนดพฤติกรรมชัดเจน เช่น แจ้งราคาใหม่และให้ยืนยันอีกครั้ง ห้ามเปลี่ยนยอดโดยที่ผู้ใช้ไม่ทราบ

## 6.2 บันทึกยอดเพิ่มเติมที่ยังไม่เคยลง

เหมาะกับการลงยอดขายนอก POS บางช่วง

ตัวอย่าง:
- POS บันทึกแล้ว 300 บาท
- มีการขายเพิ่มนอก POS 200 บาท
- ผู้ใช้เลือก “เพิ่มยอดที่ยังไม่ได้บันทึก” และกรอก 200 บาท
- ยอดขายรวมเป็น 500 บาท

ต้องอธิบายบนหน้าจอชัดเจนว่าช่องนี้ให้กรอกเฉพาะยอดเพิ่มเติม

## 6.3 กระทบยอดขายรวมทั้งวัน

เหมาะกับการกรอกยอดขายจริงทั้งวันแล้วให้ระบบเทียบยอดที่มีอยู่

ตัวอย่าง:
- POS 300 บาท
- ยอดเพิ่มเติมที่เคยยืนยันแล้ว 100 บาท
- ยอดขายจริงทั้งวัน 500 บาท
- ระบบเสนอเพิ่มอีก 100 บาท
- ยอดรวมสุดท้ายเป็น 500 บาท

การคำนวณต้องพิจารณารายการที่มีผลทั้งหมด รวมยอดสรุปที่ยืนยันไปก่อนหน้าและรายการคืนเงินตามนิยามที่กำหนด ไม่ใช่ลบเฉพาะ POS ทุกครั้ง

ต้องแยกอย่างน้อยตาม:
- ร้าน
- วันทำการ
- ช่องทางชำระ
- บัญชีรับเงินที่เกี่ยวข้อง

เงินโอนที่ไม่ทราบบัญชีต้องให้ผู้ใช้ระบุหรือพักเป็นรายการที่ต้องตรวจสอบ ห้ามเดาบัญชีปลายทาง

หน้าจอต้องแสดง:
- ยอดที่บันทึกแล้ว
- ยอดจริงที่ผู้ใช้กรอก
- ส่วนต่างที่จะสร้าง
- ผลต่อยอดขายและยอดเงิน
- เหตุผลก่อนยืนยัน

เมื่อยอดจริงต่ำกว่ายอดที่บันทึก:
- ห้ามลบบิลหรือลดยอดอัตโนมัติ
- ให้ตรวจว่ามีบิลซ้ำ คืนเงิน หรือกรอกผิด
- ใช้ขั้นตอนแก้ไขที่มีสิทธิ์และ audit trail

ให้กำหนดด้วยว่ายอดจริงหมายถึงยอดก่อนหรือหลังคืนเงิน และใช้ความหมายเดียวกันทั้ง UI, API และรายงาน

# 7. การป้องกันรายการซ้ำและการทำงานพร้อมกัน

ธุรกรรมสำคัญต้องรองรับ idempotency

อย่างน้อยครอบคลุม:
- บันทึกขาย
- ยอดขายเพิ่มเติม
- กระทบยอดขาย
- รายจ่ายและการจ่ายเงิน
- โอนเงิน
- คืนเงิน
- ปิดวัน

พฤติกรรมที่ต้องได้:
- request เดิม key เดิม payload เดิม ต้องไม่สร้างธุรกรรมซ้ำ
- key เดิมแต่ payload ต่าง ต้องปฏิเสธด้วยข้อผิดพลาดที่ชัดเจน
- หาก client timeout หลัง server commit แล้ว ส่งซ้ำต้องได้ผลลัพธ์ของรายการเดิม
- ต้องกำหนด scope ของ key และ enforce ด้วยฐานข้อมูล

การกระทบยอดและปิดวันต้องป้องกัน race condition เช่น:
- สองอุปกรณ์ยืนยันยอดสรุปพร้อมกัน
- มีการขายระหว่างที่อีกเครื่องกำลังปิดวัน
- ส่งปิดวันซ้ำ

เสนอวิธี locking หรือ version checking ที่เหมาะกับ PostgreSQL พร้อม transaction boundary

อย่าพึ่งปุ่ม disabled หรือ in-memory lock เพียงอย่างเดียว

# 8. การเงินและบัญชีเงิน

แยกแนวคิดต่อไปนี้ให้ชัด:
- ยอดขาย
- เงินรับ
- รายจ่าย
- เงินจ่าย
- เงินเติมทุน
- เงินถอนส่วนตัว
- เงินโอนระหว่างบัญชี
- เงินสดขาดเกิน

บัญชีเงิน เช่น:
- เงินสดร้านก๋วยเตี๋ยว
- บัญชีรับโอนร้านก๋วยเตี๋ยว
- เงินสดร้านเบเกอรี่
- บัญชีรับโอนร้านเบเกอรี่

หากบัญชีธนาคารเดียวใช้ร่วมสองร้าน ต้องอธิบายการแยกบัญชีจริงออกจากการระบุร้านของธุรกรรม เพื่อไม่ให้นับยอดเงินธนาคารซ้ำ

## 8.1 รายจ่าย

รองรับ:
- ร้านที่เกี่ยวข้อง
- วันที่เกิดรายการ
- หมวด
- จำนวนเงิน
- รายละเอียด
- สถานะชำระ
- บัญชีที่จ่าย
- หลักฐานถ้ามี

หมวดตั้งต้น เช่น วัตถุดิบ ค่าเช่า ค่าแรง ค่าน้ำ ค่าไฟ ค่าเดินทาง และบรรจุภัณฑ์

หากยังไม่ชำระ ห้ามลดเงินในบัญชี

MVP ไม่จำเป็นต้องมีระบบเจ้าหนี้เต็มรูปแบบ แต่ต้องกำหนดขอบเขตให้ชัด เช่น รองรับยังไม่จ่ายและจ่ายเต็มจำนวนก่อน ส่วนการผ่อนชำระหลายครั้งอาจทำภายหลัง

การซื้อวัตถุดิบต้องไม่ถูกนำไปอ้างเป็นต้นทุนสินค้าที่ขายทันที ใน MVP ให้บอกได้ว่าเป็นรายจ่ายซื้อวัตถุดิบ ส่วนการตีมูลค่าสต็อกและต้นทุนขายอยู่ในระยะถัดไป

- เติมทุนทำให้เงินเพิ่ม แต่ไม่ใช่ยอดขาย
- ถอนใช้ส่วนตัวทำให้เงินลด แต่ไม่ใช่ค่าใช้จ่ายดำเนินงาน
- ทุกธุรกรรมต้องมีผู้ทำรายการ วันที่ บัญชี และหมายเหตุ

## 8.3 โอนเงิน

- บัญชีต้นทางลด ปลายทางเพิ่ม
- จำนวนเงินโอนหลักต้องเท่ากัน
- ไม่ทำให้รายได้หรือรายจ่ายรวมเพิ่ม
- บันทึกทั้งสองฝั่งใน transaction เดียวกัน
- หากมีค่าธรรมเนียม ให้บันทึกแยกอย่างชัดเจน
- ป้องกันโอนไปบัญชีเดิมและตรวจยอดเงินตามนโยบายที่กำหนด

## 8.4 สมุดเคลื่อนไหวเงิน

ให้มี cash ledger หรือ money movements ที่อ้างอิงธุรกรรมต้นทาง

ห้ามปล่อยให้ Sale กับ Money Movement เป็นรายการอิสระที่ต่างฝ่ายต่างเพิ่มยอดเงินซ้ำได้

กำหนด:
- ประเภทต้นทาง
- การเชื่อมต้นทาง
- unique constraint ที่เหมาะสม
- วิธี reversal
- วิธีคำนวณและตรวจสอบยอดคงเหลือ

ถ้าใช้ source_type/source_id แบบ polymorphic ต้องอธิบายข้อจำกัดด้าน Foreign Key และวิธีป้องกัน reference ที่ไม่มีจริง หรือเลือก schema ที่ enforce ความสัมพันธ์ได้ดีกว่า

# 9. วันทำการและการปิดยอด

ใช้ timezone Asia/Bangkok สำหรับวันทำการของร้าน

แยก:
- เวลาที่เหตุการณ์เกิด
- เวลาที่ server บันทึก
- business_date ที่รายการสังกัด

เก็บ timestamp อย่างเหมาะสม และอย่า derive วันขายจาก timezone ของ server โดยไม่ตั้งใจ

MVP ใช้วันปฏิทินไทยเป็นค่าเริ่มต้น ส่วนร้านที่ขายข้ามเที่ยงคืนให้ระบุเป็นเรื่องที่ต้องรองรับหรือข้อจำกัดอย่างชัดเจน

หนึ่งร้านมีวันทำการได้หนึ่งรอบต่อ business_date เว้นแต่มีเหตุผลให้ใช้โครงสร้างอื่น

การขายครั้งแรกของวันอาจสร้างวันทำการให้อัตโนมัติ เพื่อไม่บังคับแม่กดเปิดร้านหลายขั้นตอน แต่ต้องกำหนดวิธีบันทึกเงินทอนตั้งต้นให้ถูกต้อง

สถานะวันทำการอย่างน้อย:
- OPEN
- CLOSED

หากเพิ่มสถานะอื่น เช่น CLOSING หรือ REOPENED ให้ระบุ transition และเหตุผล

อย่างน้อยพิจารณา:
- เงินสดตั้งต้น
- เงินสดจากการขาย
- ยอดขายเงินสดเพิ่มเติม

- เงินเติมทุน
- เงินถอน
- เงินโอนเข้าออก

ให้เลือกแบบจำลองที่ชัดเจนว่าเงินสดตั้งต้นคือยอดตรวจนับยกมา หรือเป็นการโอนเงินเข้าลิ้นชักจริง ไม่ถือว่าการกรอกเงินตั้งต้นสร้างเงินใหม่เอง

POS 300 บาท เพิ่มเติม 100 บาท ยอดจริง 500 บาท ต้องเพิ่มเพียง 100 บาท

E. Idempotency
ส่ง request เดิมซ้ำหลัง timeout ต้องมีธุรกรรมเดียว
ใช้ key เดิมกับ payload ใหม่ต้องถูกปฏิเสธ

F. Race condition
สองคำขอกระทบยอดพร้อมกัน ต้องไม่เพิ่มส่วนต่างซ้ำ

G. ยอดจริงต่ำกว่า
POS 500 บาท กรอกจริง 400 บาท ต้องแจ้งตรวจสอบ ไม่ลดบิลอัตโนมัติ

H. รายจ่าย
จ่ายเงินสด 100 บาท เงินสดลด 100 บาท ยอดขายไม่เปลี่ยน
รายการยังไม่จ่ายต้องไม่ลดเงิน

I. เงินเจ้าของ
เติมทุน 1,000 บาท เงินเพิ่มแต่ยอดขายไม่เพิ่ม
ถอน 200 บาท เงินลดแต่ไม่กลายเป็นค่าใช้จ่ายดำเนินงาน

J. โอนเงิน
โอน 1,000 บาทระหว่างบัญชี ยอดเงินรวมไม่เปลี่ยนหากไม่มีค่าธรรมเนียม

K. ปิดเงินสด
ฐานเงินสด 500 บาท
ขายเงินสด 1,000 บาท
จ่ายเงินสด 200 บาท
ถอนส่วนตัว 100 บาท
เงินสดควรมี 1,200 บาท
นับได้ 1,150 บาท ส่วนต่างเป็น -50 บาท
ยอดขายยังคง 1,000 บาท

L. ปิดวัน
บันทึกธุรกรรมลงวันที่ปิดแล้วต้องถูกปฏิเสธ
การเปิดแก้ไขต้องมีสิทธิ์ เหตุผล และประวัติ

M. สิทธิ์
พนักงานร้านหนึ่งเรียกข้อมูลอีกร้านโดยตรงผ่าน API ต้องถูกปฏิเสธ

N. Rollback
ถ้าบันทึก Sale สำเร็จบางส่วนแต่ Payment หรือ Money Movement ล้มเหลว ต้อง rollback ทั้งธุรกรรม

O. Refund
คืนเงินแล้วเงินและยอดขายสุทธิเปลี่ยนถูกต้อง
คืนซ้ำหรือเกินยอดต้องไม่ได้

P. ประวัติราคา
เปลี่ยนราคาเมนูวันนี้ต้องไม่เปลี่ยนยอดบิลเก่า

ใช้ integration tests กับ PostgreSQL จริงสำหรับ constraint, transaction และ concurrency ที่สำคัญ ไม่ใช้ mock ทุกอย่างแล้วถือว่าพิสูจน์ความถูกต้องแล้ว
